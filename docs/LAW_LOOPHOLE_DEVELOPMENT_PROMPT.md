# Промпт для разработки анализатора дыр, абузов и противоречий в законке

Этот файл предназначен для нейросети-разработчика, которая будет писать код функционала в проекте ProdBot.

Важно: не придумывай архитектуру с нуля. Следуй этому промпту, текущим паттернам проекта и готовым runtime-промптам из [docs/LAW_LOOPHOLE_RUNTIME_PROMPTS.md](LAW_LOOPHOLE_RUNTIME_PROMPTS.md).

## Роль разработчика

Ты работаешь в проекте ProdBot. Нужно разработать новый функционал: **Анализатор дыр, абузов и противоречий в законке**.

Функционал должен анализировать законы RP-серверов и находить:

- противоречия между нормами;
- пробелы регулирования;
- слишком узкие формулировки;
- размытые термины;
- отсутствие процедур, сроков или санкций;
- коллизии полномочий;
- сценарии возможного внутриигрового абуза;
- рекомендации по исправлению текста законов.

Главное: не превращай это в обычный юридический RAG-ответ. Это должен быть состязательный анализатор законки, который мыслит как игрок-абузер, адвокат, обвинитель и администратор игрового проекта.

## Контекст проекта

Проект ProdBot уже содержит:

- Python Telegram bot;
- PostgreSQL;
- таблицу `law_documents`;
- текущий RAG для юридических вопросов;
- выбор проекта и сервера;
- Vertex/Gemini;
- rate limiter для AI-запросов;
- сервисный слой для части бизнес-логики.

Законы хранятся в `law_documents`.

Ожидаемые поля закона:

- `id`;
- `server_id`;
- `source_thread_id`;
- `source_url`;
- `title`;
- `content`;
- `gemini_file_uri`;
- `content_hash`;
- `last_updated`.

Существующий RAG уже умеет выбирать законы через router-модель и передавать `gemini_file_uri` в Gemini как `Part.from_uri`.

## Главный архитектурный принцип

Не привязывай анализатор дыр только к RAG.

RAG хорош для точечных вопросов, но плох для системного поиска противоречий, потому что противоречие часто находится между документами, которые по отдельности не кажутся релевантными.

Правильный пайплайн:

```text
User Intent
-> Source Selection Policy
-> Model Policy
-> LawContextBundle
-> Loophole Analyzer
-> Synthesis
-> Report
```

Отдельное замечание: начинать разработку нужно не с Telegram-кнопок, а с сервисного ядра:

```text
Source Selection Policy -> Model Policy -> LawContextBundle
```

Когда это ядро покрыто unit-тестами, анализатор и Telegram UX ложатся намного спокойнее.

## Обязательные режимы выбора источников

Реализуй единый слой `Source Selection Policy`. Он должен собирать `LawContextBundle` и поддерживать четыре режима.

### 1. `auto_rag`

Router-модель выбирает релевантные законы по запросу пользователя.

Используется для:

- конкретного кейса;
- быстрого поиска слабых мест;
- анализа задержания, обыска, наказания, полномочий;
- режима, где пользователь не хочет выбирать документы руками.

Важно:

- выбирать только законы выбранного `server_id`;
- не включать документы без `gemini_file_uri`;
- при слишком узком результате можно добавить fallback на базовые документы, если такая эвристика будет явно реализована и покрыта тестами.

### 2. `full_server`

Берутся все законы выбранного `server_id`.

Используется для:

- полного аудита законки;
- поиска глобальных противоречий;
- поиска коллизий между кодексами;
- режима “найди все, что можно абузить”.

Важно:

- если документов много, включать batch-анализ;
- не пытаться силой запихнуть слишком большой контекст в один запрос;
- корректно обрабатывать частичные ошибки batch-проходов.

### 3. `manual_select`

Пользователь сам выбирает законы из списка.

Используется для:

- экспертного анализа;
- сравнения нескольких документов;
- обхода auto RAG, если пользователь хочет полный контроль;
- анализа конкретных кодексов.

Важно:

- должен быть лимит количества документов;
- должен быть лимит примерного размера контекста;
- нельзя выбирать документы другого сервера;
- повторный выбор документа должен снимать выбор;
- нельзя подтверждать анализ с пустым выбором.

### 4. `hybrid`

Пользователь выбирает базовые документы вручную, а router-модель добавляет связанные документы.

Используется для:

- глубоких кейсов;
- анализа темы, где пользователь знает основные законы, но хочет страховку от пропуска связанных норм;
- режима “ручной выбор + умное расширение”.

Важно:

- ручные документы всегда входят в контекст;
- RAG-документы добавляются без дублей;
- пользователь должен видеть, какие документы добавлены автоматически;
- если auto RAG ничего не добавил, ручной выбор все равно валиден.

## Структура `LawContextBundle`

Реализуй внутреннюю структуру данных. Можно использовать `dataclass` или Pydantic-модель, если это соответствует проекту.

Поля:

```text
server_id: str
project_id: str | None
selection_mode: Literal["auto_rag", "full_server", "manual_select", "hybrid"]
selected_laws: list[LawContextDocument]
selection_reason: str
coverage_level: str
estimated_size: int
requires_batching: bool
model_profile: Literal["fast", "balanced", "deep", "expert"]
```

`LawContextDocument`:

```text
id: int
server_id: str
title: str
source_url: str | None
gemini_file_uri: str
content_hash: str | None
last_updated: datetime | None
estimated_size: int
selection_source: Literal["manual", "rag", "full_server", "fallback"]
```

## Model Policy

Добавь отдельный выбор моделей для этого функционала. Не используй одну глобальную модель для всех режимов.

Пользователю показываются человекочитаемые режимы:

- `Быстро`;
- `Стандартно`;
- `Глубоко`;
- `Экспертный аудит`.

Внутри кода они соответствуют профилям:

### `fast`

```text
router: flash-lite
analyzer: flash
synthesis: flash
```

Для быстрых точечных анализов и ручной выборки до 3-5 документов.

### `balanced`

```text
router: flash-lite
analyzer: flash
synthesis: flash или pro при большом числе находок
```

Для обычного анализа 5-10 документов.

### `deep`

```text
router: flash-lite
analyzer: pro
synthesis: pro
```

Для глубоких абуз-сценариев, противоречий и коллизий полномочий.

### `expert`

```text
router: flash или pro
analyzer: pro
synthesis: pro
batch mode: включен
```

Для полного аудита законки сервера.

Реальные имена моделей храни в `config.py` или в существующем конфигурационном паттерне проекта.

Пример новых настроек:

```python
LOOPHOLE_ROUTER_MODEL_FAST = "..."
LOOPHOLE_ANALYZER_MODEL_FAST = "..."
LOOPHOLE_SYNTHESIS_MODEL_FAST = "..."

LOOPHOLE_ROUTER_MODEL_DEEP = "..."
LOOPHOLE_ANALYZER_MODEL_DEEP = "..."
LOOPHOLE_SYNTHESIS_MODEL_DEEP = "..."
```

Не хардкодь model names в бизнес-логике.

## Типы анализа

Поддержи типы анализа:

- `quick_scan` — быстрый скан очевидных дыр;
- `deep_abuse` — глубокий абуз-анализ;
- `case_analysis` — анализ конкретного кейса пользователя;
- `new_law_review` — проверка нового закона перед публикацией;
- `full_audit` — полный аудит законки сервера;
- `devil_advocate` — режим “адвокат дьявола”.

## Структура результата анализа

Каждая находка должна иметь структуру:

```text
id: str
title: str
vulnerability_type: str
source_documents: list[str]
source_fragments: list[str]
issue_summary: str
abuse_scenarios: list[str]
affected_roles: list[str]
gameplay_impact: str
severity: Literal["low", "medium", "high", "critical"]
confidence: Literal["low", "medium", "high"]
fix_recommendation: str
```

Нельзя пропускать ссылки на источник. Если модель выдала находку без источника, такая находка должна быть отброшена или помечена как низкая уверенность и не попадать в финальный отчет без явного предупреждения.

## Этап 5. Batch-анализ больших контекстов

Для `full_server` и `expert` нужен многошаговый анализ.

Pass 1:

- анализ каждого документа отдельно;
- поиск внутренних дыр.

Pass 2:

- извлечение норм и группировка по темам:
  задержание, обыск, оружие, суд, прокуратура, полиция, сроки, санкции, доказательства.

Pass 3:

- поиск противоречий между группами документов.

Pass 4:

- финальный synthesis:
  дедупликация, severity, confidence, сценарии, фиксы.

Чек-лист:

- [ ] Batch-анализ работает при 20+ документах.
- [ ] Ошибка одного batch не ломает весь аудит.
- [ ] Есть промежуточные результаты.
- [ ] Финальный synthesis объединяет повторы.
- [ ] Логи показывают прогресс.

Unit-тесты:

- [ ] Документы разбиваются на batch по лимиту.
- [ ] Порядок документов сохраняется.
- [ ] Частичная ошибка batch возвращает partial report.
- [ ] Дубли из разных batch объединяются.
- [ ] Финальный отчет сортируется по severity.
- [ ] `requires_batching=True` запускает batch-пайплайн.
