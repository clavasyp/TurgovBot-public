# Аудит качества Overlay-поиска законов — 2026-07-25

## Короткий вывод

Текущий ranker из `216f142` нельзя безопасно «улучшать на глаз»: известные кейсы
защищены тестами, но до этой задачи не сохранялось, что пользователи реально
спрашивали и какие статьи получили. Поэтому в этой итерации порядок выдачи не
меняется. Добавляется измерительный контур: вопрос, компактный снимок ответа,
состояние каждой поисковой ноги и read-only отчёт.

Журнал помогает найти подозрительную выдачу, но сам по себе не является разметкой
«правильно/неправильно». Для этого далее нужны проверенный golden-набор и явный
feedback/open/copy/favorite, связанный с `search_event_id`.

## Найденные общие классы риска

### 1. Неоднозначные автоматические синонимы

Read-only production-аудит показал 84 273 approved-синонима; текущие табличные
синонимы имеют `source=auto`. Около 10 164 exact-пригодных строк (12,1%) находятся
в группах, где одна формулировка ведёт сразу к 2–9 статьям. При этом
`synonym_exact` считается сильным сигналом и отключает дополнительный vector boost.

Удалять или резко ослаблять такие синонимы нельзя: часть многозначности реальна.
Безопасный следующий эксперимент — collision-aware вес только в shadow-режиме.

### 2. Обычное число может стать «номером статьи»

Текущий detector считает code-кандидатом любой целочисленный токен. Поэтому
«3 раза стрелял», «скорость 200» или «штраф 5000» могут отключить legal/intent
rewrites, хотя число не является статьёй. В журнал теперь отдельно пишется
`code_signal_reason`, чтобы проверить более строгий detector offline, прежде чем
менять production.

### 3. RRF знает порядок, но почти теряет абсолютную силу сигнала

Cosine/FTS-confidence в основном задают порядок внутри поисковой ноги. После этого
RRF даёт слабому и сильному кандидату близкие голоса, а несколько коррелированных
keyword-ног суммируются как независимые доказательства. Абсолютный публичный
`score` нельзя трактовать как вероятность правильности.

В trace сохраняются статусы, кандидаты, доступные raw scores/confidence и
фактические веса. Это позволит offline сравнить calibrated fusion и family caps,
не показывая кандидатный порядок пользователю.

### 4. Общая очистка запроса теряет отношения между словами

Обычная нормализация удаляет часть предлогов и служебных слов. Role-aware fix
сохранил направление только для строгого класса «действие → защищённая цель».
Расширять hard-pin на новые ситуации без данных опасно. Будущий вариант должен
иметь отдельное смысловое представление запроса, сохраняя роли, отрицания и цель,
а lexical cleaned оставить для SQL-ног.

### 5. Есть риски данных и покрытия

- `doc_title` вне целевого `code_doc` почти не участвует в общем поиске;
- keyword-ноги в отдельных местах могут видеть chapter/section;
- в production есть группы одинаковых названий статей;
- FRIDA-рецепт обрезает body и не включает `doc_title`;
- слабая fuzzy-выдача сейчас не умеет честно сказать «уверенного ответа нет».

Менять FRIDA-рецепт можно только новым versioned embedding-space с полным
backfill и сравнением на одном снимке каталога.

## Что реализовано без изменения выдачи

- Migration 022 и append-only таблица `law_search_events`.
- Bounded `asyncio.Queue`: пользовательский запрос делает только `put_nowait`.
- Один batch-writer пишет события в PostgreSQL; ошибка/таймаут/переполнение
  приводит только к drop telemetry и никогда не меняет HTTP-ответ.
- Сохраняются success, empty, 503, 500 и cancelled.
- Снимок ответа ограничен 20 карточками: rank, stable article ID, code, title,
  doc title, RRF score и sources. Snippet, полный текст и санкция не дублируются.
- Сохраняются normalizer features, intent, code reason, path `code_doc|hybrid`,
  статусы/кандидаты/latency ног, vector mode, веса и intent priority IDs.
- Нет raw user/device/HWID/IP/JWT/API-key. Срок хранения по умолчанию — 90 дней,
  очистка идёт небольшими batch под advisory lock.
- Read-only анализатор показывает operational failures отдельно от сигналов
  ручной проверки: empty, single weak-leg top, малый относительный gap,
  нестабильный top у одинакового запроса в одной версии, p50/p95 и режимы.

Запуск агрегированного отчёта:

```bash
python scripts/analyze_law_search_logs.py --days 7
python scripts/analyze_law_search_logs.py --days 30 --server memphis --json
```

CLI намеренно не читает и не печатает тексты вопросов или идентификаторы
пользователей. Для подозрительных событий он показывает только случайный
`event_id`; сам вопрос и компактный ответ остаются в защищённой таблице для
отдельной ручной разметки администратора.

По умолчанию CLI загружает не больше 20 000 свежих событий и явно сообщает, если
окно было обрезано. Большие выборки пока анализируются в памяти, поэтому
`--max-events` повышать постепенно. Сигнал «одинаковый запрос дал разный top-1»
тоже не является автоматическим дефектом: без catalog fingerprint причиной может
быть штатное обновление самой законки.

## Безопасный план улучшения точности

1. Накопить журнал и собрать стратифицированную выборку: подозрительные события
   плюс 10–20% обычных «здоровых» ответов.
2. Создать golden corpus для десяти каталогов: допустимые/запрещённые top,
   контрастные роли, отрицания, намерения и честное отсутствие аналога.
3. Считать candidate ranker в shadow: collision-aware auto-synonyms и более
   строгий code detector. Пользователю продолжает отвечать baseline.
4. Затем проверить calibrated fusion с raw score и ограничением коррелированных
   ног. Изменения normalizer/новых ног требуют отдельного read-only replay.
5. Только после разметки рассматривать reranker и порог «уверенного ответа нет».
6. Выпускать через shadow → tester canary → общий rollout с kill switch.

Обязательные gates для любого ranker change:

- ноль регрессий на critical top-1 и forbidden-top;
- известный правильный ответ не опускается ниже baseline;
- Recall@1 не хуже baseline, MRR/Recall@3 выше;
- false intent-pin и no-answer false positives не растут;
- p95, timeout/degraded-rate и доля `full` не ухудшаются;
- baseline и candidate сравниваются на одном catalog fingerprint и FRIDA-space;
- все изменившиеся top проходят ручной review до production.
